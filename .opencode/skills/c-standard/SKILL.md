# C Standard (cold-chain-monitor-c-rp2350)

This is the coding standard for the pure-C firmware and test suite in this repo.
Every function, global, macro, `typedef`, struct, and member must comply.
Vendored libraries and auto-generated files are **excluded** (see Scope).

## Scope: what must comply

Comply (all C code you own):

- Every `*.c` and `*.h` in this repo that you write or edit, including `src/`,
  `include/`, `test/`, and the in-repo test harness `test/harness/`
  (everything except the exclusions below).

Excluded (do not touch):

- `include/packet_artifact.h` and `build/generated/` (auto-generated by
  `scripts/gen_packet.py`)
- Vendored or fetched third-party libraries (e.g. Pico SDK)

> The repo does **not** vendor any test framework. `test/harness/` is our own
> minimal harness and is fully in scope. Do not add third-party code that
> violates this standard; write a compliant in-repo alternative instead.

## Rule 1: No blank lines inside a function or method body

There must be **zero** blank lines within any function body.

- A function body is the `{ ... }` that follows a signature, i.e. a `{` whose
  preceding non-whitespace character is `)`. In C this covers function
  definitions AND the control-flow blocks inside them (`if/for/while/switch`):
  all of those braces are inside a function body, so blank lines are forbidden
  at any depth within the body.
- Blank lines are allowed **only** to separate functions or types from each
  other (outside bodies). Struct/union/enum member declarations are **not**
  function bodies; blank lines may separate them.
- A "blank line" is a line that is whitespace-only (including a line of indent
  spaces). Lines that contain code, a `//` comment, or a `/** ... */` block are
  NOT blank and are untouched.

Examples:

```c
// WRONG: blank lines (line 2 and 4) inside the body
static void clear_frame(uint8_t *buf, size_t len) {
    size_t i;
                      // <- blank, remove
    for (i = 0u; i < len; ++i) {
        buf[i] = 0u;
    }
}
```

```c
// CORRECT: no blank lines inside the body
static void clear_frame(uint8_t *buf, size_t len) {
    size_t i;
    for (i = 0u; i < len; ++i) {
        buf[i] = 0u;
    }
}
```

### Comments inside bodies

- Keep comment lines in place; only remove the genuinely blank lines.
- A multi-line `/* ... */` comment can span blank-looking comment lines:
  those are comment content, not blank lines; leave them. Only whitespace-only
  lines count.

## Rule 2: Eight-line function-body limit

There must be **at most eight lines** in any function body.

- A **body line** is any line between a function's opening `{` and its closing
  `}` that contains code, including declarations, statements, control-flow
  lines, and continuation lines of a multi-line expression.
- **Doxygen comment blocks** (`/** ... */`) are documentation, not code, and
  are not counted.
- **Blank lines** are already forbidden by Rule 1, so they never count.
- A line that is only an opening `{` or a closing `}` is not counted, but the
  opening `{` in a control-flow line such as `if (x) {` does count with that
  line.
- The signature line is not counted.
- The limit applies to **every** function you own: firmware, headers with
  inline code, file-local `static` helpers, and test cases. If a body exceeds
  eight lines, extract a helper that obeys the same limit, or move shared state
  to file scope.

```c
// WRONG: 9 body lines
static int process(uint8_t *buf, size_t len) {
    size_t i;
    int total = 0;
    for (i = 0u; i < len; ++i) {
        total += buf[i];
        if (total > 100) {
            total = total % 100;
        }
    }
    if (total < 0) {
        total = 0;
    }
    return total;
}
```

```c
// CORRECT: fold_byte keeps process at 5 body lines
static int fold_byte(int total, uint8_t value) {
    total += value;
    return (total > 100) ? (total % 100) : total;
}

static int process(uint8_t *buf, size_t len) {
    size_t i;
    int total = 0;
    for (i = 0u; i < len; ++i) {
        total = fold_byte(total, buf[i]);
    }
    return total;
}
```

## Rule 3: Doxygen documentation compliance (100%)

Every entity in scope must carry Doxygen documentation.

### File header

Every file starts with this exact structure (or the MIT license header of
`include/*.h` and `src/*.c` followed by the Doxygen block):

```c
/**
 * FILE: test_cold_chain_monitor_and_security.c
 *
 * DESCRIPTION:
 * Comprehensive test suite for the RP2350 Cold Chain Agricultural
 * Environmental Monitor.
 *
 * BRIEF:
 * Native unit test runner for cold-chain-monitor-c-rp2350.
 *
 * AUTHOR: Kevin Thomas
 * DATE: September 2026
 */
```

### Functions

Every function (including file-local `static` helpers and test cases) gets a
doc block immediately above it with `@brief` and, when applicable,
`@param`/`@return`:

```c
/**
 * @brief Initialize the classroom monitor state machine.
 *
 * @param void No parameters.
 * @return bool true when all submodules initialized.
 */
bool monitor_init(void) {
    g_ready = true;
    g_next_tx_us = time_us_64() + (uint64_t)COLD_CHAIN_MONITOR_TX_INTERVAL_MS * 1000u;
    return true;
}
```

Use `@param void No parameters.` / `@return void` when there are none
meaningful. If a function takes parameters, name every one:

```c
/**
 * @brief Transmit one fixed-size telemetry frame over the transceiver.
 *
 * @param uart Pointer to the UART peripheral the radio is wired to.
 * @param payload Pointer to fixed-size frame bytes.
 * @param len Number of payload bytes to transmit.
 * @return radio_result_t Detailed transmit outcome.
 */
radio_result_t radio_send_frame(uart_inst_t *uart, const uint8_t *payload,
                                size_t len);
```

### Globals, `#define`s, `typedef`s, struct members, and constants

Each gets a `@brief` block:

```c
/**
 * @brief Onboard LED GPIO pin number.
 */
#define COLD_CHAIN_MONITOR_LED_PIN 25u

/**
 * @brief Fixed telemetry frame buffer size in bytes.
 */
#define COLD_CHAIN_MONITOR_FRAME_SIZE 48u
```

For struct and enum types, each member declaration is preceded by a `@brief`
block:

```c
/**
 * @brief Sensing result codes returned by the one-wire state machine.
 */
typedef enum sensor_result {
    /**
     * @brief A clean reading passed the response checksum.
     */
    SENSOR_RESULT_OK = 0,
    /**
     * @brief The response checksum failed to validate.
     */
    SENSOR_RESULT_CRC_ERROR = 1,
    /**
     * @brief A response edge never arrived inside the timeout.
     */
    SENSOR_RESULT_TIMEOUT = 2,
    /**
     * @brief The sensor was called in an uninitialized policy state.
     */
    SENSOR_RESULT_POLICY_ERROR = 3,
} sensor_result_t;
```

### Locals

Simple loop iteration locals need no annotation. Named/explicit locals carry a
`@brief Declaration of X.` block immediately above (no blank line between the
comment and the declaration, and no blank line between consecutive blocks):

```c
void test_radio_hex_digits(void) {
    /**
     * @brief Declaration of rcv.
     */
    radio_rcv_t rcv;
    TEST_ASSERT_EQUAL(RADIO_RESULT_OK,
                      radio_parse_rcv("+RCV=00a7,2,ok,-3,2", &rcv));
    TEST_ASSERT_EQUAL_HEX16(0x00A7u, rcv.sender);
}
```

> Note: the `@brief Declaration of <name>.` blocks are a repo convention and
> MUST be preserved when present. Blank lines inside function bodies are the
> only thing removed; never delete a Doxygen comment block.

## Rule 4: Naming and structure conventions

- Files: `snake_case` (`radio.c`, `monitor.c`, `test_cold_chain_monitor_and_security.c`).
- Constants/`#define`s: `UPPER_SNAKE` (`COLD_CHAIN_MONITOR_LED_PIN`, `SENSOR_BIT_COUNT`).
- Types (`typedef` names): `snake_case_t` (`sensor_result_t`, `dht_reading_t`).
- Functions: `snake_case`, prefixed with the module name (`sensor_read`,
  `radio_send_frame`, `display_format_lines`, `test_monitor_step_transmits`).
- Struct/enum members: `snake_case` or `UPPER_SNAKE`.
- File-local (static) symbols: `g_`-prefixed state, `snake_case` private
  helpers (`g_sensor_ready`, `wait_while_level`).
- `#ifndef` include guards at the top of headers.

## Rule 5: Pitfalls to avoid

- Never include secrets or credentials in plaintext readably in the binary.
- Never use leading-underscore+capital identifiers (`_Foo`); reserved.
- Don't touch auto-generated `include/packet_artifact.h` or `build/generated/`.
- Don't add `//` editor comments; keep the Doxygen style consistent (`/** */`).
- Use `<stdint.h>` fixed-width types; never rely on plain `int` width for wire
  data or telemetry state.
- No implicit narrowing conversions that truncate values.
- Keep stack usage bounded for RP2350 microcontroller execution.

## Auditing: how to verify compliance

Run the C standard audit scanner. It reports blank lines inside function
bodies, functions whose body exceeds eight lines, and functions missing a
Doxygen `@brief` block:

```bash
python3 scripts/audit_c_standard.py
```

No output means every owned `.c`/`.h` file satisfies Rule 1, Rule 2, and the
function-documentation part of Rule 3 across `src/`, `include/`, and `test/`
(generated files excluded).

Run the unit test suite:

```bash
python3 scripts/run_tests.py
```

Verify 100% line coverage of owned firmware modules:

```bash
python3 scripts/check_coverage.py
```

Rebuild the firmware using Pico SDK:

```bash
mkdir -p build && cmake -S . -B build -G Ninja -DPICO_BOARD=pico2 -DPICO_PLATFORM=rp2350-arm-s && cmake --build build
```
